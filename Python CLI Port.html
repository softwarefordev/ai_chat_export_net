## What the tool actually is

~/.cursor/chats/<project>/<chat>/
        meta.json          store.db
            |                  |
            v                  v
        catalog            blob graph
     schemaVersion 1     sqlite, read-only
            |                  |
            +--------+---------+
                     |
         picker, or --id
                     |
                     v
              transcript filter
         query / agent stretch / tools
           verbose / detail / times
                 /       \
                v         v
           HTML page    Markdown
        (default)     (--markdown)

Six modules, and they stay separate in a port:

  • **Catalog** walks */*/meta.json, skips anything that is not schema version 1, and sorts by last update. "This workspace" is the launch directory, case-insensitive on Windows.
  • **Store** is the risky piece. store.db is SQLite with a hex-encoded meta row and a blobs table. The root blob is sometimes a list of 32-byte ids, sometimes a protobuf-shaped message with no .proto. The reader is a heuristic: try aligned ids, try a hand-rolled wire walk, and fall back to scanning. Role messages are JSON objects that start with { or [. Unrecognized blobs and PNGs that are not attached to a turn are named in a footer and left out of the body.
  • **Transcript** turns that message list into User and Agent sections. It pulls user_query, conversation_summary, and cursor_commands out of the text with string matching. This is not well-formed XML.
  • **HTML and Markdown** are hand-built strings. The page is self-contained: dark unless --theme light, a 30rem navigator of user turns only, no script, no external address.
  • **Picker** is a raw terminal state machine. Arrows, Enter for a file-name line, Esc, i to show the chat id. On Windows it reads keys with msvcrt; elsewhere it uses termios. The block cursor and the full-screen redraw are ANSI writes.
  • **CLI** is argparse: --id, --theme, --tools, --verbose, --detail, --markdown, --out, --name, --chats-root. --name requires --id and conflicts with --out. A terminal stderr gets a ... / .. / . cycle until the path or the error is printed.

## What changes shape in .NET, and what should not

The store reader should be ported as the same heuristic. A generated protobuf library needs a schema this file does not have, and it would reject blobs the Python walker accepts by returning "not protobuf" and falling through. SQLite is the one real dependency (Microsoft.Data.Sqlite). Everything else in the Python project is the standard library.

The picker should stay a small state machine. A console widget library will fight the column rules, the name line that keeps the list on screen, and the blinking block cursor in the cell after the draft. Console.ReadKey replaces both msvcrt and termios. Cursor shape is still an ANSI write, same as the Python tool.

The transcript filter and both renderers can move almost line for line. Switching the tag extraction to an XML parser would change which turns survive.

Two Python requirements do not survive the move:

  • python -m … has no counterpart. A global tool, or dotnet run, replaces it.
  • The installed command can stay ai-chat-export. Two installs with that name on one PATH will collide, so the name is a choice only if both CLIs stay in use.

I would keep the flags, the picker keys, the file names, and the HTML. The Python tests are the oracle for that. A byte-for-byte HTML match is achievable because the renderer has no library in the middle. Timestamps are the soft spot: Python %b follows the process locale, so month abbreviations can differ from a fixed English DateTime format.

The .NET repo can hold its own session-export spec, written from the running behavior, with the command and the module requirement stated for .NET. That is a new capability in this repo, not a sync from the Python one.
